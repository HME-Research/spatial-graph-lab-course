# Decision record — v0.1 (12 November 2026)

## Confirmed for prototype
- Repo: `spatial-graph-lab` (private during development). Workshop: **Graph, Rules & Space**.
- Browser-only app; React + TypeScript + Vite; React Flow for abstract 2D graph, React Three Fiber/Three.js for 3D views; Vitest and Zod. No Graphology, API/backend, multiplayer or database initially.
- Single graph document shared by Graph 2D / Graph 3D / Voxels / Architecture. Optional split view with two independent mode selectors, shared node/edge selection, independent cameras.
- Graph 2D is an **abstract diagram of the entire 3D building**; not floor-level slices. Preserve the graph's manual diagram layout separately from physical coordinates.
- Sparse unbounded-in-principle integer grid; configurable safety limits. First example can be 3 × 3 cells, but this is **not** the global grid boundary. Default cell dimension proposed: 3m × 3m × 3m, configurable centrally.
- Student-extensible node types; graph relationships determine shared boundary type; node type determines exposed façade configuration. No imported geometry required for initial prototype.
- Horizontal adjacency: no edge=solid wall; `door`=door opening; `open`=no separating wall. Vertical edges conceptually supported as `atrium` or `vertical-access`, with first full geometry implementation deferred.
- Owner-only local plan and development instructions must be gitignored; no core code required in this specification package.

## Architecture refactor — Stage 1 (14 November 2026)
- Target layout: `core/` generic reusable capabilities; `app/` application behaviour, building generation and UI composition; `student-api/` stable student extension interface; `projects/` independent projects (`types/`, `designs/`, `algorithms/`). No `src/`, `lib/`, `domains/` or `apps/`.
- Stage 1 extracts a generic graph core into `core/graph` (no spatial, architectural, UI or JSON-format assumptions; directed/undirected; self-loop and parallel-edge policy per graph). The former graph module moves unchanged in behaviour to `core/spatial` and uses the core through `designGraph(doc)`.
- v1 JSON document format, IDs, grid coordinates, edge kinds and their face-adjacency rules, issue codes/messages, commands and viewer contracts are unchanged; golden tests in `core/spatial/compat.test.ts` pin them.
- Moving `core/spatial`, `core/architecture`, `core/viewer` and `core/app` under `app/`, and creating `student-api/` and `projects/`, are later stages.

## Architecture refactor — Stage 2 (14 November 2026)
- Modules were classified by what they do and depend on, not moved wholesale. `core/` keeps reusable capabilities; `app/` holds the application. Both are owner-maintained and protected from student edits by the shared instructions and CODEOWNERS (advisory; neither is access control).
- The v1 design document (schema, edge kinds, validation, commands, serialisation, `designGraph`) moved from `core/spatial` to `app/document`; the golden compatibility test and snapshot moved with it unchanged (`app/document/compat.test.ts`).
- `core/spatial` now contains only reusable, dependency-free integer-grid maths (`GridCoord`, `gridKey`, face adjacency, `FACE_DIRECTIONS`, `neighbourCell`). Grid maths does not depend on the graph core. The document schema reuses `GridCoord` with a compile-time equality guard.
- `core/architecture` moved to `app/building`. Views, view contracts and registry moved to `app/views`; shell and inspector to `app/`.
- `core/viewer` keeps generic camera/orbit canvas, `fitCameraToBounds`, click-vs-drag, picking, selection (now structural, document-free) and the coordinate mapping. Storey levels, occupied-cell bounds, the ground-grid computation and the empty-document camera fallback are grid/document-specific and live in `app/views/three` — deliberately not generalised as universal viewer functionality.
- Dependencies are not a strict linear chain: `core/graph`, `core/spatial` and `core/viewer` are mutually independent where possible; core never imports `app/`, `student/` or `projects/`; app modules may import core. Enforced by automated import-boundary tests.
- `@core/*` / `@app/*` aliases are defined once in `tsconfig.json` and read by Vite/Vitest via `resolve.tsconfigPaths` (no new dependency). They are a convenience, not access control.
- The unused `PlaceholderView` was deleted. Not part of Stage 2: `student-api/`, `projects/`, new graph algorithms, a generic `IssueList`, UI redesign, spatial solver, new architectural rules.

## Student API and projects — Stage 3A (14 November 2026)
- `projects/` replaces `student/`. One project is active at a time; each has `project.ts` and optional `types/`, `designs/` (JSON) and `algorithms/` (TypeScript). The canonical built-in example moved, byte-identical, to `app/document/examples/`; `projects/example-gallery/` holds a teaching copy pinned by a drift test.
- `student-api/` holds compile-time contracts, identity `define…` helpers and a few pure helpers; it validates nothing and imports only `core/graph` and `core/spatial`. `app/extensions` performs all runtime validation (Zod) and execution. Project code imports only `@student-api` and its own files.
- Generic graph algorithms are analysis-only and see ids, endpoints and the graph policy only. There is no generic document, so generic node creation is not supported; a future generic document would need its own schema. Spatial algorithms see the schema-v1 node and edge records (including edge attributes) and return `add-node` (explicit cell, registered type, declared typed attributes), `add-edge` (existing v1 kinds only) or `set-node-attribute` operations.
- Transformations: per-operation permission and semantic checks on a private draft, full `validateDocument` of the final state, identity-based conformance non-regression; all-or-nothing; the result is a preview and the original document is never changed. Attribute writes are limited to declared attributes of valid registered types; undeclared/legacy values are never written or removed; defaults are resolved on read and never written implicitly.
- Diagnostics: invalid or duplicate definitions are disabled with conspicuous errors (no silent fallback); an undefined `typeId` keeps the existing fallback; conformance never blocks loading a v1 document. Selection: `?project=`, then `VITE_SGL_PROJECT`, then `example-gallery`; an unknown requested project is an error. Failed activation falls back to the built-in example with persistent diagnostics; a missing/invalid `defaultDesign` loads nothing.
- Appearance: colours stay `typeColor` (custom colours deferred); project façades override the example façades, which remain the fallback. Example-gallery reproduces the gallery/studio/storage façades exactly.
- Not part of Stage 3A: UI integration (activation in `App`, appearance in views, inspector support, algorithm controls, transformation preview) — Stage 3B. No new dependencies, schema change, spatial solver or edge kinds.

## Application integration — Stage 3B (14 November 2026)
- The app activates one project at startup through the Stage 3A runtime (`activate`, `resolveStartupDesign`); no second loading path. The project menu switches project in place and records `?project=` in the URL. Activation never runs an algorithm.
- Diagnostics are persistent (never auto-dismissed): failed activation shows the built-in example under an error headline; a missing/invalid `defaultDesign` opens nothing. Unsaved changes are detected by document identity against the last loaded/exported document; switching project, opening a project design, loading the example or opening JSON asks before discarding them.
- `ViewProps` gained one optional, read-only `project` field (`ProjectViewContext`: active project, conformance, façade provider). Without it views behave as before. Colours stay `typeColor`; the example project reproduces the existing façades exactly (tested on the full architecture output). A broken type definition renders with a closed façade (`windowFraction: 0`), an Architecture-view notice and a ⚠ in Graph 2D — never another type's façade.
- Inspector: registered type labels; typed controls generated from declarations (number, text, boolean, enum) whose values are checked by the runtime's `checkValue` before a `set-node-attributes` command; invalid stored values stay visible and kept; defaults are shown as hints and never written; undeclared/legacy attributes are edited in a separate free-form editor that cannot overwrite declared keys. Without a valid registered type the previous free-form editor is unchanged.
- Algorithm panel: lists algorithms (disabled ones selectable to show why, but not runnable), parameter drafts validated by the runtime's `validateParameters`, results from `runAlgorithm`. Analyses only display values (rows select nodes). Transformations show a validated preview; Apply replaces the document with `preview.after` in one step only if the current document is the exact object the preview was computed from (otherwise stale, refused); Discard drops it.
- `projects/starter-template/` is a minimal copyable project (one type, one analysis, one transformation, one design). `npm run check:project` runs `app/extensions/projectCheck.test.ts`, which loads every project exactly as the app does and fails on invalid definitions/designs or algorithms that fail on the default design with default parameters (conformance warnings are only printed).
- Not part of Stage 3B: undo/redo, showing previews or analysis values inside the 3D views, custom colours, a project manager, new edge kinds or schema changes.

## Workspace and camera — Stage 4A (14 November 2026)
- The application occupies exactly the browser viewport (no `max-width`). Header and project bar take their natural height (the project bar's expanded diagnostics scroll inside it, capped at 35 vh); the workspace takes the rest. Below 900 × 560 px the page scrolls and panels stack instead of squeezing the views.
- The workspace is one or two view panels plus a sidebar. Each panel has a header with its view-mode selector; the first panel's header holds the Single/Split toggle. The sidebar has Inspector and Algorithms tabs, scrolls on its own and can be collapsed to a rail; both tabs stay mounted, so tab switches and collapsing keep drafts and results. Inspector and algorithm content can no longer change any viewport's size.
- The raw node/edge tables under the workspace were removed. The inspector shows the design summary (name, description, schema, counts, storeys) when nothing is selected, and the selected item's stored record and diagram position under a collapsed *Stored data* section.
- Camera fitting (`core/viewer`): `fitCameraToBounds` now takes the canvas aspect ratio and fits the box's eight corners against both the vertical and the horizontal field of view (margin 1.15), instead of a bounding sphere against the vertical field of view only. `SceneCanvas` computes the fit itself from a `Framing` (bounds + minimum radius), because only the canvas knows its aspect ratio.
- Camera state: the camera starts automatically fitted; while it is, resizes refit it. The first orbit, pan or zoom switches it to a user pose that is never moved automatically again; **Fit view** returns to the fitted state. Document and selection changes never move the camera (unchanged).
- The Architecture view now uses the shared `SceneCanvas` (its own lighting, tone mapping, on-demand rendering and no orbit damping are options), replacing its private canvas, framing heuristic and camera rig; its "Frame all" button is now "Fit view" like the other 3D views, and its picking uses the shared click-vs-drag rule.
- Layout state lives in `Workspace`: panel modes and a per-panel memory survive single/split changes. The second panel is unmounted in single view (no hidden renderer); when reopened, each view restores its camera (3D) or viewport (Graph 2D) from the panel memory (`app/views/panelMemory.ts`, synchronous storage, optional for views). The first panel is never remounted by a layout change.
- Not part of Stage 4A: undo/redo, circular 2D nodes, connect mode, inspector movement controls, analysis colouring, new algorithms, schema or Student API changes, new geometry rules.

## Undo/redo and document history — Stage 4B (15 November 2026)
- History stores document **snapshots**, not inverse commands (`app/session/history.ts`, generic and pure; `app/session/documentSession.ts`, the open document's session). At most 100 previous steps; each step carries a readable label shown in the Undo/Redo tooltips. Opening a document (project activation or switch, project design, Load example, Open JSON) starts a new, empty history only after the unsaved-changes confirmation and only when the new document is valid.
- One step per successful change: each graph command that changes the content (add/delete node, add/delete/change edge, node type, attributes, grid move, one completed diagram drag) and each applied transformation, however many operations it has. Rejected commands and commands that leave the content unchanged are not recorded and do not clear redo. Recording after an undo discards the redo steps.
- Only the document is in history: selection, cameras, panel layout, sidebar state and algorithm results are not. After undo/redo a selection whose node or edge no longer exists is cleared; a pending Graph 2D edge-kind choice is cancelled by any document change.
- Clean state replaces the Stage 3B identity test: a document is modified when its **content signature** (canonical JSON with sorted object keys; node/edge order significant) differs from that of the last loaded or exported document. Undoing back to that content clears the indicator; redoing away restores it; editing back to equal content is also clean. Export moves the clean baseline only after the download was started without error, and keeps history. Exported JSON and the files in `projects/` stay distinct: exporting never writes project files, and the project design file is only the initial baseline.
- Every change of the shown document (edit, undo, redo, open) increases a document **revision**. Algorithm results record the document and revision they ran at; a preview can be applied only at exactly that revision, so undo/redo makes previews and analyses stale even when redo returns the identical document object. Running the algorithm again is the new validation step.
- State transitions are computed outside React updater functions and handed to React as values (no side effects in updaters, StrictMode-safe). Shortcuts: Ctrl/Cmd+Z undo; Ctrl/Cmd+Shift+Z and Ctrl+Y redo; ignored inside text inputs, textareas and contenteditable elements so native text undo keeps working. No new dependency.
- Not part of Stage 4B: persistent history across reloads, history of selection/camera/layout, merging consecutive edits, circular 2D nodes, connect mode, schema or Student API changes.

## Schema v2 contract gate — Gate 0 (15 November 2026)
- The parallel MVP wave builds against frozen v2 contracts in `docs/CONTRACTS-V2.md`: `@app/document/v2` (schema, validation, migration, read/write, footprints, display ids, appearance settings) and the new pure `@app/spatial` layer (relationship resolution, occupancy, spatial edits, v2 commands, the `DesignPort`).
- Additive: the running app, the v1 module and its golden tests are unchanged. The app switches to v2 at integration. `ViewProps` gains one optional field, `design?: DesignPort`. `IssueCode` gains four v2-only codes.
- Relationships are `access` / `open` and need no adjacency. Spatial status (`direct` / `routed` / `unresolved`) is derived, never validation. Rooms are integer boxes (`grid` minimum corner + `size`); room overlap is invalid. Resizing is anchored at the minimum corner. Taking generated connector cells needs explicit confirmation.
- v1 → v2: `door`/`vertical-access` → `access`, `open`/`atrium` → `open`. The mapping is lossless because the v1 kind is recoverable from the rooms' contact. Read v1 and v2; write v2 only.
- Straight-connector routing is a stub at Gate 0 (`routing-unavailable`). It and the Student API adaptation belong to 02-spatial-engine.

## Programme 2026-11 — Integration gate I2: wall ↔ graph (16 November 2026)
Contracts: `docs/CONTRACTS-V3.md` §1 (`PlanWallView`, `PlanView.activeWall`) and §4 (`DesignPort.onScenarioCommand`, wave 2 D UI semantics).
- **Wall click semantics:** a shared wall between two rooms is the only interactive wall, in the Building and the Plan alike. Clicking it opens a wall panel. Add creates an Access (door on the clicked wall) or Open relationship in the one authoritative graph, in one undo step. A related wall offers change / move door here / remove, never a second edge.
- **Room selection on wall click:** the click also selects. A wall of two related rooms selects their relationship. Any other shared wall selects its owner room, as wall clicks did before the panel. This keeps the room editor available; an I2 audit had found that the panel cleared the selection. After "Remove relationship" the owner room is selected, so no stale edge selection remains. With that room selected, its editor handles can take the pointer over the same wall; close the panel or deselect to click the wall again.
- **Explicit removal UI:** unresolved relationships are removed only through Graph 2D "Remove invalid connections". It lists them, checked by default, the student can uncheck rows, and confirming is one `remove-edges` undo step. Geometry edits never remove edges.

## Imported façades (3DM) — owner decisions D1–D9 (17 November 2026)
Supersedes the Gate F BLOCKED-DECISION on binary assets. Spike: `app/assets/facadeAdapter.ts` (promoted from `3dm-spike/`). Contracts: CONTRACTS-V2 §1 (`facade`), CONTRACTS-V3 §2 (embedded assets). D6, D7 and D9 were revised by the owner the same day (marked **revised**).
- **D1 dependency:** `rhino3dm`, exact pin, lazily loaded. 8.17.0 (the spike's version), 8.32.2 and 8.35.0 passed the same reader, import and persistence tests; **8.35.0** (latest stable Rhino 8 library, browser WASM 2.67 MB vs 2.61 MB) is pinned and browser-verified. MIT, no dependencies. A test keeps `package.json`, the installed version and the reader label equal.
- **D2 reader:** adapted from the owner's SpatialCore `@spatialcore/rhino3dm-import@0.3.0` (owner-approved reuse; no package dependency). Copied/adapted code is marked with a provenance header (`app/assets/rhino/reader.ts`, `loader.ts`). Meshes, Brep-face and Extrusion cached render meshes, blocks (nested, composed parent × child, depth ≤ 8), layer/object colours and glass-by-name; geometry without a render mesh is meshed on import (D9). Material groups are one per object (and layer style) when the model has ≤ 32 such pairs, else one per layer. Curves, points, hidden objects and objects on layers that are off are left out and listed. Rhino's black default layer colour draws as a neutral grey.
- **D3 Vite:** `build.rolldownOptions.external: ['ws']` (rhino3dm's Node-only `require("ws")`). The reader, the rhino3dm glue and its WASM load only through `import('@app/assets/rhino/browser')` on the first import (`app/assets/lazyLoading.test.ts`; production build checked: the entry chunk names the lazy chunk only). rhino3dm 8.35.0 also references `node:fs` / `node:crypto` in that branch; Vite externalises them for the browser (warnings, verified harmless in Edge).
- **D4 storage:** the normalised mesh (not the `.3dm`) is embedded in the project file (`embedded-mesh-v1`), so autosave, Save As, export and open carry it without rhino3dm. Integrity by SHA-256 (synchronous, `app/assets/binary.ts`) with a hash-keyed cache so autosaves do not re-verify unchanged payloads. Projects without façades keep `{policy: 'none'}` byte-identically.
- **D5 bounds:** `.3dm` ≤ 20 MB (before parsing); ≤ 100 000 triangles; extent ≤ 50 m; depth ≤ 1 m; ≤ 32 assets and ≤ 20 MB decoded binary per project (warning above 5 MB).
- **D6 conventions (revised):** draw in Rhino's Front view — x along the wall, z up, the outside facing −y; units converted once through `zUpToYUp`; unitless files need an explicit unit. Which side faces out is a live per-function choice (Outside −Y / +Y, stored as `facade.flip`): a 180° turn about the module's vertical centre line, never a mirror (it was an import-time option, which made re-importing the same file look unchanged). The 3 m nominal module: Repeat fits one bay (cell width × storey height). Width and height fitted exactly, depth never scaled. **The module replaces the wall:** its back sits on the wall's inner surface (half a wall thickness inside the centre plane) and the Building view does not draw the wall or Designer windows of a covered face. The Building model, Plan and façade metrics are unchanged.
- **D7 placement (revised):** per Function only. Each function card has two subsections, **Façade** and **Roof**; Façade → **Geometry** is Open (no exterior walls) / Automatic (walls with the Designer's windows) / Import (an imported 3DM module, with Import .3dm…, the façade menu, Outside, Repeat / Stretch and Materials…). There is no Defaults section and no design-wide default façade (`facadeDefault` and `'none'` were removed before release). Undoable design settings; switching geometry is one command. **Repeat** = one module per exterior wall bay; **Stretch** = one module per wall run (`groupWallRuns`: contiguous coplanar exterior bays of one room on one storey). Fits scaled more than 5 % are reported per function. Open-sided functions get no module; shared walls and interior doors / open sides never do (walls BESIDE an open-air connector are exterior and do). The Façade and Roof subsections are collapsible (open until collapsed; remembered per function in this browser). Import's façade menu and Import .3dm… share one row; Outside and Placement share one row.
- **D10 door / open bays (owner 2026-11-17):** a function's imported façade may also name an optional **Door bay** and an optional **Open bay** module (`facade.door` / `facade.open`, each with its own Outside). They replace the façade bays where an open-air connector meets the room with a door / an Open relationship (the connector's `outside` endpoint faces), one module per bay; a bay whose module is not set keeps the automatic geometry (glass door, open threshold). The Open threshold stays as the invisible pick target. Materials have three finishes, **Solid / Glass / Open** (Open = not drawn, e.g. a doorway), and the same asset can have different materials per use (Materials… tabs: Façade / Door bay / Open bay; a bay is "Same as Façade" until changed), stored on the project asset (`bayMaterials`). **Project → Imported façades** (collapsible) manages the same library outside the Designer: Import .3dm…, Rename, Materials…, Remove. **Removing a used façade** asks first (listing scenarios and functions); confirmed, every use in every scenario becomes Automatic (a bay that used it: automatic bay), one undo step per affected scenario; the asset removal itself is not undoable. "Remove unused" still skips used ones. The **Materials dialog shows a 3D preview** of the model with the materials being edited: clicking a part (or its name) selects it in both; Open parts show as faint ghosts so they can still be picked.
- **Vertical access in the Building (owner 2026-11-17):** a vertical-access relationship is drawn as the slab opening only; the vertical marker box (read as a lift shaft) and its legend entry were removed. The Plan keeps its access symbol.
- **Materials:** Materials… opens a small dialog listing the façade's parts with Solid / Glass and a colour each (`ProjectController.setFacadeAssetMaterials`); project-level like the façade (every function and scenario using it), not undoable; the mesh and the asset id are unchanged.
- **D8 blocks:** nested blocks are expanded (tested with a scaled outer placement); deeper than 8 levels or recursive references are left out with a warning.
- **D9 non-mesh geometry (revised):** geometry without a saved render mesh is meshed on import in the browser (`app/assets/rhino/tessellate.ts`; rhino3dm has no mesher): Brep faces (and extrusions via `toBrep`) from their trim loops — planar faces exactly in their plane (outline verified flat, `isPlanar` is loose), curved faces in the surface's (u, v) parameters, refined to ≈ 0.1 % of the object's size, untrimmed faces as a grid; outlines that cross themselves are resampled finer; untrimmed `Surface` objects as a grid; SubD by Catmull–Clark (3 levels within budget) from the control net (`Mesh.createFromSubDControlNet`; rhino3dm 8.35's own SubD subdivision/limit calls do not work). Checked against Rhino's own render meshes on ~3,800 faces of real files (928 curved): mean area difference 0.02–1 % per file. Rhino's render mesh is still used wherever the file has one. Polygon triangulation uses `earcut` 3.2.4 (ISC, exact pin, no dependencies; as in SpatialCore `geometry-core`), loaded only with the lazy 3DM chunk. Not available through rhino3dm: SubD creases/sharp edges (smoothed), Brep trims of polar (singular) faces (tiny caps can be off).
- **Not done:** Plan view does not draw modules (it shows the wall line); façade modules on interior doors/open sides; Rhino materials/textures (colours from layers and objects, then the Materials dialog); normals are flat-shaded; genuine Rhino 7-authored and real façade `.3dm` files were not available for testing (synthetic archives 60/70/80 and one genuine Rhino 8 file were).

## Uploaded transforms; an informative Transform ⓘ (25 November 2026, owner decision; amends "Uploaded analyses")

## Tutorial review fixes: toolkit check that cannot pass silently, Command Prompt, claim the id early, source/repos (26 November 2026, owner decision)
- **`check:toolkit`:** `npm run check:toolkit -- -t <toolkit-id>` is unchanged for students but now runs `lab/scripts/check-toolkit.mjs` (no dependency). It reads the id from `-t <id>`, `-t=<id>`, `--toolkit <id>` or a bare `<id>` (Windows PowerShell 5.1 drops `--`, so npm swallows `-t` and only the id arrives) and passes it to `toolkitCheck.test.ts` as `SGL_CHECK_TOOLKIT`, never as vitest's name filter, which skipped every test and passed when nothing matched. A requested toolkit that is not found fails with a beginner message (`No toolkit "…" was found.
